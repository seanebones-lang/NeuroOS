# NeuroOS Engineering Roadmap

NeuroOS is being built as a dependable personal operations system. It must preserve the user's
real state, explain where generated records came from, fail visibly, and recover safely after a
restart.

## Current baseline

The repository now has a working foundation:

- PostgreSQL is the shared source of truth for the API and worker.
- Alembic owns schema changes and runs before application services in Compose.
- Protocol failures are recorded and returned as failures; the system does not create fabricated
  fallback plans.
- Agent tool calls use validated JSON arguments and return tool results to the model.
- Task start, pause, and resume preserve an exact user-authored next action across restarts.
- Tasks generated by a protocol carry the exact protocol run that created them.
- Authenticated task writes enforce ownership, schedules, lifecycle transitions, and dependent
  deletion rules through one service.
- The API, CLI, and worker use the same protocol and task-context services.
- The automated suite covers model behavior, scheduling, agent tools, protocol failure, task
  recovery, ownership isolation, and protocol-run isolation.

This is a development baseline. It is not yet a production release.

## Phase 1: Core integrity

Goal: every state transition is valid, attributable, and safe to retry.

- Route remaining internal task-generation paths through the task service where appropriate.
- Add idempotency keys to protocol execution and task-generating endpoints.
- Prevent concurrent morning runs from producing duplicate plans.
- Record structured protocol step outcomes, provider, model, latency, and error category.
- Add API integration tests against PostgreSQL for authentication, ownership, and rollback cases.

Exit gate:

- Repeating a request cannot duplicate a plan or corrupt task state.
- Cross-user identifiers cannot create or expose relationships.
- Every generated task can be traced to one run and its recorded step outcomes.

## Phase 2: Security and operational controls

Goal: make unsafe configuration difficult and abuse visible.

- Refuse production startup with the development signing secret or missing required settings.
- Restrict CORS to configured origins.
- Add login and protocol-run rate limits.
- Introduce short-lived access tokens and a revocable refresh-token flow.
- Define secret rotation and provider-key handling.
- Add dependency, container, and repository security checks to CI.
- Publish `SECURITY.md` with supported versions and reporting instructions.

Exit gate:

- Production configuration passes an automated startup check.
- Authentication abuse is throttled and recorded.
- The main branch passes tests, migrations, dependency checks, and image scanning in CI.

## Phase 3: Observability and recovery

Goal: detect failures quickly and prove that data can be restored.

- Emit structured logs with request, user, protocol-run, and task correlation IDs.
- Add metrics for request latency, protocol duration, provider failures, queue lag, and worker health.
- Add readiness checks for PostgreSQL, Redis, migrations, and configured model providers.
- Define service-level objectives for API availability and protocol completion.
- Automate PostgreSQL backups with retention and encryption.
- Run scheduled restore drills and record recovery time and recovery point results.
- Add graceful shutdown and abandoned-run reconciliation.

Exit gate:

- An operator can identify a failed request and its protocol run from one correlation ID.
- A clean environment can be restored from backup within the documented recovery targets.
- Interrupted workers leave runs in an explicit recoverable state.

## Phase 4: Product workflow

Goal: turn the reliable core into a useful daily system.

- Build a focused daily-plan interface around start, pause, resume, complete, and defer.
- Show why each task was selected and which run created it.
- Let the user review and edit plans before activation.
- Add calendar integrations through explicit provider adapters and sync cursors.
- Add notification preferences, quiet hours, and delivery history.
- Measure completion, deferral, interruption, and planning accuracy without inventing productivity
  claims.
- Meet keyboard navigation, screen-reader, contrast, and reduced-motion requirements.

Exit gate:

- A user can plan, interrupt, resume, and close a day without using the CLI.
- External sync is retryable, deduplicated, and auditable.
- Accessibility checks and core user journeys pass before release.

## Phase 5: Release discipline

Goal: make releases repeatable and reversible.

- Create staging and production environments with separate databases, secrets, and provider keys.
- Add versioned API contracts and migration compatibility checks.
- Automate deployment with health checks and rollback.
- Publish operator runbooks for provider outages, database incidents, and failed migrations.
- Establish release candidates, changelogs, and a defined support window.
- Run a limited pilot and promote only after the integrity, security, recovery, and workflow gates
  above have evidence.

## Immediate next slice

Add idempotency to protocol execution and prevent concurrent morning runs from producing duplicate
plans. Build this on the task service and protocol-run provenance so a retried request can return its
original run safely.
